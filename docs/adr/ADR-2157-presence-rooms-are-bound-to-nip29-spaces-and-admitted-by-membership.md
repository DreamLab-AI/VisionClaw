# ADR-2157 — Presence rooms are bound to NIP-29 spaces and admitted by membership

Plan: `docs/proposals/spatial-rooms/PLAN.md` §3, §4 (VisionClaw). Forum-side decisions are in the nostr-rust-forum repository (its ADR-2030, ADR-2031, ADR-2032, all proposed there). Those numbers are that repository's, not this tree's ADR-2030 to ADR-2032.

## Context
- A presence room is a free string the client sends in `auth`. `RoomId::parse` checks the prefix, `sha256-12-` and 12 hex characters, not that the hex derives from anything (`crates/visionclaw-xr-presence/src/types.rs:42-55`). The server never mints a room URN; the XR default is a constant (`xr-client/scripts/graph_scene.gd:83`).
- Any DID that passes the Schnorr handshake joins any room: no membership check, no cap (`src/handlers/presence_handler.rs:273-305`; `JoinRejection` has only `DuplicateMember` and `Internal`, `src/actors/presence_actor.rs:166-171`).
- A NIP-29 group's identity is `(home relay pubkey, group id)`; the id alone collides across relays (`h=general`). `sha256-12` is 48 bits, too short across federated spaces (ADR-2023).
- `src/services/nostr_bridge.rs` is one-way, connects once per event and has no NIP-42 AUTH (`:184-212`). The only NIP-42 code is the AUTH builder in the `vault` CLI (`crates/vault/src/nostr.rs:203-228`); there is no persistent authenticated subscriber.
- The 0x43 wire hash is a non-cryptographic FNV pair (`types.rs:62-78`): a routing key, and it stays one.
- No relay-membership read exists in VisionClaw, and the forum relay does not yet sign 39000-39002 (plan §4).
- The cross-vendor audit (`docs/proposals/spatial-rooms/AUDIT-DECISIONS.md`) found that a bare "fails closed" does not bound revocation latency, that a hash with no registry lets any string claim a room, and that `moved_to` needs a two-home handover nobody has designed. Round 2 found the round-1 clocks incompatible (60 s guarantee against a 70 s threshold) and `created_at` unfit to order state. Decisions 4, 5, 7, 11 and 13 encode rulings C1 to C3 and the unbound-room ruling.

## Decision
Presence rooms for NIP-29 spaces are bound to the space and admitted by relay membership. Concretely:

1. **Room id and golden vector.** The form is `urn:visionclaw:room:nip29-<32 lowercase hex>`: the first 16 bytes of SHA-256 over exactly this byte string, with no separators:
   - the 24 ASCII bytes of the domain tag `visionclaw/room/nip29/v1`;
   - the 32 raw bytes of the home relay's x-only public key (not hex);
   - a `u16` big-endian length of the group id in bytes;
   - the group id's UTF-8 bytes. The group id must match `[a-z0-9_-]{1,255}`; any other value is refused at mint.

   **Golden vector (REQUIRED, committed with the mint and passing before any admission code ships).** Key bytes `00 01 02 … 1f`, group id `general`. The hashed input is `766973696f6e636c61772f726f6f6d2f6e697032392f7631` ‖ `000102…1f` ‖ `0007` ‖ `67656e6572616c`. The expected URN is `urn:visionclaw:room:nip29-e5488c85b92647026b5d54e422122a6f`. (The author computed this with SHA-256 on 2026-10-30; the committed test must reproduce it, and any mismatch blocks activation.) The home key is in the input, so a host rename keeps the room and a fork (a new home key) is a different room.
2. **One mint, one registry.** `room_from_group()` in `src/uri/mod.rs` is the only constructor of the form (IDENTIFIER-taxonomy Invariant 2). It is also the only writer of a server-side **room binding registry** mapping each `nip29-` URN to `(pinned home key, group id)`. `RoomId::parse` and `uri::parse` accept the grammar, but `RoomAdmission` rejects any `nip29-` URN with no registry entry, so a well-formed URN that was never minted is refused. The `sha256-12` form stays parseable and unchanged (Invariant 3).
3. **Key pinning.** The operator pins each home relay's public key out of band, in configuration. It is never trusted on first use. The pinned key is the relay's signing key, not the NIP-11 `pubkey` admin contact. NIP-11 `self` is discovery only: it may suggest a key to pin, never confers one, and a mismatch with the pinned key refuses every join and subscription for that relay. A home key change is a re-home, which is a fork (decision 6).
4. **One revocation clock (C1).** Constants, shared with forum ADR-2031: snapshot lease **L = 60 s**; relative clock-error budget **S = 10 s** (nodes run NTP, an operational prerequisite); live-session re-check interval **C = 10 s**. A 39002 is fresh while `now - created_at <= L + S` (70 s) and is refused as future-dated if `created_at > now + S`. Stale means **deny**, for new joins and for sessions already joined: the snapshot becomes inadmissible after L + S, and an existing session is closed at the next check, within C thereafter (not at L + S). `RoomAdmission` re-checks every live session every C and closes a session that no longer passes, with `room_kicked`. Admission is checked again after the session is registered in the room, to close the join-versus-removal race. An unknown group, an unreachable relay or a missing snapshot also deny. **The single end-to-end guarantee is D = 90 s**: from authoritative removal at the home to closure of every presence session (and, via ADR-2161, every dataspace stream). Voice is not covered by D. **Voice is weaker, by ruling (final audit #7).** LiveKit cannot revoke an issued token, so voice is bound by **D_voice = 2L + 2S + C = 150 s** from removal at the home: the latest token a removed member can hold is minted before their snapshot goes stale (at most L + S after removal) and expires L later; within that window each rejoin is removed by the reconciler within C, so the member may be reconnected for at most C at a time, and after it rejoin is impossible (ADR-2160 D3, D6). Presence and dataspace streams keep D, and rejoin there is refused outright. **Exception:** during a LiveKit API partition, voice participants stay connected until the API returns (ADR-2160 D6, operator sign-off); presence and dataspace streams stay bound by D. D covers a withheld removal (L + S = 70 s), plus C, plus margin. The home publishes a removal immediately and re-signs at least every 30 s when nothing has changed (forum duties; without them every bound room stops admitting, which is the intended failure). Verification tests assert D.
5. **Ordering (B1, C3, consumer side).** The home keeps an admission sequence and every 3900x carries `["rev", <u64>]`, its monotonically increasing group-state revision. State order is by `rev`; `created_at` is wall-clock time, never bumped, used for freshness in decision 4 and to order equal-`rev` heartbeats (snapshot replacement), never events of different `rev`. VisionClaw replaces a cached 39002 (or 39000) only on a strictly greater `rev`, or on an equal `rev` with a strictly greater `created_at` and identical content (a heartbeat, which renews freshness; forum ADR-2031 D2) and keeps a **persisted watermark per room and per kind**, holding (`rev`, `created_at`, event id, content digest). The content digest is SHA-256 over the canonical JSON of the pair (`tags`, `content`), with `created_at`, id and signature excluded, so an equal-`rev` heartbeat is compared against it after a restart without persisting the membership list. An equal-`rev` event with different content is rejected as equivocation. A replayed or late-older snapshot never replaces a newer one, including across restarts. After a restart it may rehydrate the exact accepted event (same id) from the subscription, but never treats it as newer. Only (`rev`, `created_at`, id, content digest) is persisted, not the membership list or the signed payload. A fresh start with no watermark accepts the first snapshot that is fresh and verifies against the pinned key. The home-side rules (admission-order application of 9000 to 9022, at most one snapshot per kind per second) are forum ADR-2030 and 2031 duties; the `storage.rs:97-139` guard in the forum is their prerequisite.
6. **No move.** There is no `moved_to` and no alias from an old URN to a new one. A fork is a changed authoritative identity: a different home key (or group id). A change of hostname or relay endpoint under the same pinned key is **not** a fork; identity is `(home key, group id)` and the room is unchanged. A fork gets a new room URN with fresh admission and nothing carried over (members, caps, history, watermark). A move needs an authenticated two-home handover and is a future ADR (audit M5).
7. **Unbound rooms (operator-confirmed 2026-10-30).** A `sha256-12` room is not in the registry. It is still allowed, for compatibility, as **presence only**: **never** a LiveKit token (ADR-2160), no claim of membership, an authenticated DID (the handshake) required, and subject to the member cap of decision 9. The setting `presence.bound_only` defaults to **false** and is set **true when P2 activates**, after which unbound rooms are refused. The XR default room (`graph_scene.gd:83`) is unbound, so P2 must move it to a bound room before `bound_only` becomes true. Until P2 the XR default keeps working as compatibility presence; refusing it is not an option at activation.
8. **Admission port.** `RoomAdmission` is a port beside `IdentityVerifier` in `crates/visionclaw-xr-presence/src/ports/mod.rs`, injected through `PresenceHandlerState`. `handle_auth` calls it after `RoomId::parse` and before the registry entry is created (`presence_handler.rs:273-281`), and again after registration (decision 4). It fails closed on every error path. The handshake is unchanged: it proves the DID, and membership is a separate check on that DID.
9. **Member cap.** Every room, bound or unbound, has a member cap, enforced inside the room join (`room.rs:42`, `presence_actor.rs:664`) so that concurrent joins cannot race past it. No cap exists in code today (`JoinRejection` has no full-room case), so this is new work; the default is 32, configurable as `presence.max_members_per_room`.
10. **Subscription and bridge key.** The NIP-29 adapter holds one persistent NIP-42-authenticated connection to each pinned home relay, subscribed to 39000 and 39002 for the groups it serves, with reconnection and backoff and an audited library for the AUTH answer. The bridge key proves only itself and carries no user authority (ADR-2013). For `private` or `hidden` groups its read access is a **scoped read grant**, separate from membership: it never confers write, never appears in 39002, and the forum issues and revokes it. If the grant is revoked, those groups deny.
11. **Kick and metadata.** Removal (9001) or a ban sends a `room_kicked` text frame and closes the socket within D. A `room_meta` text frame carries the 39000 name, about and picture. Both are JSON text frames on `/ws/presence`, recorded in `docs/PROTOCOL-registry.md`. No binary opcode is allocated and the frozen `visionclaw-wire` crate does not change.
12. **Membership cache.** A disposable derived projection of the home relay's signed 39002 (`docs/DATA-authority-erasure.md`). The relay is the write-master. The member list is held in memory, rebuilt from the subscription, never backed up. Decision 5's watermark is the only persisted item.
13. **Zone-backed groups (B4, C2).** For a group projected from a cohort or zone, the cohort is the membership authority; the group is a projection. VisionClaw reads only the projected 39002. The home signs a 39002 only while the projection is coherent with the cohort, recording `["proj", <cohort-rev>]`; if the projection lags or fails it **stops re-signing**, so every consumer goes stale within L + S and denies. A projection failure with a healthy signer and network is a required test. Enforcing that membership events on such a group are refused or routed through the cohort is a forum duty (forum ADR-2030).
14. **Scope.** VisionClaw consumes relay membership. It adds no identity federation and no delegation, so this stays inside ADR-2013's deferral (see Consequences). Codescape is out of v1 (ADR-2143); any shared room-binding code reaches it only through crates.io (I9/I10).

Rejected alternatives:
- **Reuse `sha256-12`.** 48 bits and no relay identity in the input; two nodes' `h=general` would collide. Lengthening it would break the cross-substrate `sha12()` contract (ADR-2023).
- **Reuse `urn:visionclaw:group:<team>#members`.** Team-scoped, not relay-scoped; it names a membership, not a place.
- **Trust NIP-11 `self` on first use.** An attacker who answers first at a hostname becomes the home. Lost to out-of-band pinning.
- **A `moved_to` alias.** Lost because it lets the old home's last signed claim redirect admission without any proof that the new home accepts the same members. See decision 6.
- **Fail open on an unreachable relay, or leave joined sessions alone on a stale cache.** Both admit removed members for as long as the relay is down. A refused join is recoverable; an admitted non-member is not.
- **A new binary opcode for kick and metadata.** Control traffic is low-rate; a text frame needs no fixture in the three golden suites.
- **NIP-42 on `/ws/presence`.** The Schnorr handshake already proves the DID; only the bridge leg needs NIP-42.

## Consequences
- **Easy:** one deterministic room per space on every node; removal reaches the live socket within D = 90 s in the worst case, and sooner when the subscription delivers it; two clients never disagree about a room's id; a forged `nip29-` URN gets nowhere.
- **Hard:** presence depends on a reachable home relay that re-signs every 30 s. An outage or a stalled signer makes the last good snapshot inadmissible after L + S (70 s); existing sessions close at the next check, within C thereafter, and D = 90 s remains the end-to-end guarantee. The registry and the per-kind watermarks are new server state to test across restart. Unbound rooms need a cap that does not exist yet.
- **Foreclosed:** a hand-typed bound room; a second mint; inferring membership or administration from the bridge's read grant (the grant adds no 39002 entry and no write authority; any membership the forum separately grants the bridge so it can post, forum ADR-2030 D5, is the forum's decision and confers nothing here); moving a room between homes in v1; voice for unbound rooms; ordering events of different `rev` by `created_at`.
- **ADR-2013 scope.** ADR-2013 defers enterprise identity federation (OIDC/SAML/LDAP/SCIM) and NIP-26 delegation; it is silent on relay or node federation. This ADR stays inside it because the principal is still the user's own key proven by the handshake, 39002 is an authorisation input, and the bridge's AUTH proves only the bridge. If the bridge signs as a user or a room accepts a delegated key, ADR-2013's review trigger fires.
- **Cross-reference:** ADR-2161's `space:<nip29-room-urn>` ACL reuses `RoomAdmission` and this registry; ADR-2160 mints voice tokens only for registered rooms.
- **Revisit** if the home key cannot be pinned before room creation, if D = 90 s proves too long or the 30 s re-sign too costly for the forum, or if Codescape gains NIP-98 and is to host bound rooms.
- **Counter-examples that block activation:** a DID absent from 39002 joins (including with the relay unreachable); a removal does not close the socket within D; a 39002 with `now - created_at > L + S` is accepted, or one with `created_at > now + S`; a replayed or late-older snapshot (lower `rev`) replaces a newer one, or does so after restart; a heartbeat 39002 suppresses a valid older 39000; a `nip29-` URN absent from the registry is admitted; a join racing a removal survives; a lagging cohort projection keeps being admitted while the signer is healthy; an unbound room gets a voice token, or an unauthenticated DID joins one; the golden vector fails.
- **Follow-on:** `docs/IDENTIFIER-taxonomy.md`, `docs/PROTOCOL-registry.md`, `docs/IDENTITY-authority-chain.md` and `docs/DATA-authority-erasure.md` carry proposed entries. They become current-state entries when the code lands.

## Activation prerequisites
`depends_on` lists code dependencies only. Activation is a separate gate (`AUDIT-DECISIONS.md` C9, step 4 of the cross-repo order):
- Forum ADR-2030 (applicable gate E1 to E6 and D3 coherence) and ADR-2031 (signed, `rev`-bearing, coherent 39002 with the 30 s re-sign) are live.
- The golden vector passes, and the tests behind the counter-examples above, including the D = 90 s assertion and projection failure with a healthy signer.
- The operator sets `presence.bound_only = true` at P2 activation; the member cap defaults to 32 (`presence.max_members_per_room`), which the operator may override.
- ADR-2161 `space:` activates after this ADR, not before. Voice (ADR-2160) is deferred by the operator: no room, bound or unbound, gets voice until that deferral is lifted.
