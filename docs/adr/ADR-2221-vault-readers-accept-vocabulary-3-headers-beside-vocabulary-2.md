# ADR-2221 — The vault readers accept vocabulary 3 headers beside vocabulary 2, through one shared reading

## Context

visionGraph's vocabulary 3 is decided and being rolled out (ontomark's reader shipped in 0.10.0; the corpus is still vocabulary 2). It changes what a page header says: `visibility` replaces `public` on working pages, `generated.by` becomes a `did:nostr:` principal with the instrument in `via`, `sources` gain `rel`, `locator` and pins, and working pages gain `Brief`, `Proposal`, `Belief` and `Procedure` with a per-type `status`. VisionClaw reads headers in three places that did not share code: the domain parser (`PageMeta`, the sync and KG gate), `vault-core` (`Page`, `OkfBlock`, the `vault` CLI and build) and the publication census. By reading the code, and by tests that failed on the old code, a v3 header was mis-read, not rejected: a working page that lost `public` fell out of the graph (ontomark 0.9.0 measured 171 public working pages become 170 on that mistake; the same follows here because the gate read only `public`), a `did:nostr:` stamp was dropped without a word (`Stamp::from_yaml` returned `None`), and a human's `verified` entry lost its weight (`is_human_verified` is a prefix test). The old VisionClaw code was not run against a migrated copy.

## Decision

1. **One reading, in `vault-core`.** `visibility`, the stamp and actor grammar, the principal roster, per-type status and current recall live in `vault_core::{visibility, okf, principal, roster, lifecycle}`. `visionclaw-domain` depends on `vault-core` and calls them; the census in `vault` does too. There is no second parser to drift.
2. **Which key publishes a page is decided by the vault and the vocabulary version, as ontomark decides it.** `visibility` is honoured **only** for a working page whose vault vocabulary declares version 3 or later (`Rules::Visibility`); every other page (every knowledge page at any version, every page under vocabulary 2, a source with no vocabulary) is public by `public: true` alone and `visibility` is ignored (`Rules::PublicFlag`). Every reader takes the `Rules`; there is no context-free reading, and the compiler lists the callers. Under `Rules::Visibility` the answer fails closed: `visibility: public` that `public: false` contradicts is **not public** and is reported as `Problem::Conflict`, `public: true` with `visibility: shared` or `private` is not public (conflict), an unknown `visibility` is not public, and `public: true` with no `visibility` is not public (an unmigrated page; ontomark flags the missing key). The census refuses to build over a conflict. A re-rendered page writes each key as authored and never derives one from the other: a migrated page gains no `public`, a v2 page renders as before, a conflicting page keeps both keys (an earlier version of this record said visibility decides and dropped `public` on re-render; both were wrong). The version reaches the readers from the vault's own `ontology/vocabulary.yaml`: the sync takes it from the corpus source's vocabulary and **stops if that vocabulary exists and will not load** (it never guesses a version); `vault build` and `vault validate` use the vocabulary they were given; the vault kind is the vault directory (`working/`), and for a repo path only a path under `working/` is a working page.
3. **Stamps name a principal through the roster.** `did:nostr:<64 lowercase hex>` is an `Actor` beside `human:<npub>`; `via` is kept; `human:<npub>`, a `did:nostr:` key and an `also` key resolve to one canonical principal. Human certification follows the roster: a `human:` actor is human, a `did:nostr:` actor only if the roster resolves it to `kind: human`, so Fungible Token keeps its human `verified` after its stamp is rewritten. This reaches the promotion state machine too (`PromotionState::of_with`, `promotion::apply_with`): a human's `did:nostr:` approval is accepted, an organisation's is refused; the roster-less `of` and `apply` keep the vocabulary 2 rule. bech32 is the maintained `bech32` crate, pinned `=0.11.1` (the release ontomark pins), checked against the NIP-19 vector and the seven published npub/hex pairs.
4. **Nothing is dropped silently.** An unreadable `generated`, `verified` or `sources` value is listed (`OkfBlock::problems`, `PageMeta::stamp_problems`) and reported by `vault validate` as `INVALID_STAMP` (warning under vocabulary 2, error under 3); a re-render writes it back as authored. Typed sources keep `rel`, `at`, `locator`, pins and unknown fields; an id-only source is legal.
5. **The new kinds are recognised.** The vocabulary loader reads the vocabulary 3 `working_types` map and `working_required`, `valid-from`, `valid-to`, `supersedes`, `superseded-by` and `statements` are known keys from version 3, and `vault validate` checks `status` per type (memory kinds take `draft`, `approved`, `superseded`, `invalidated`, `archived`; a vocabulary may declare a set for a type). `lifecycle::is_recallable` is the one recall rule: an `approved` memory kind inside its valid-time window; never a brief, a proposal, or a superseded, invalidated, archived or draft page.
6. **Drift from ontomark fails the build, for the pages the fixture holds.** ontomark's vocabulary 3 fixture vault is vendored byte-for-byte (hash manifest) with VisionClaw's own pages, and `golden.json` holds ontomark's answers for every page under **both** vocabulary versions, generated by calling ontomark's predicates. For publication the asserted rule is stronger than equality: VisionClaw must **never read as public a page ontomark keeps private**, for every page under vocabulary 2 and 3 in its own vault; the one page where it reads *less* than ontomark (`working/VcConflictPublic` under 3, the fail-closed conflict) is named in the test. Four knowledge pages that carry `visibility` pin that it is ignored there. The other parity (principal, certification, recall) is asserted equal; one difference is deliberate and named: a `human:<name>` resolves through the roster label, so the page names the same principal before and after its migration. The claim is about the fixture (and a read-only run over the 11,649 real pages with the real vocabulary, version 2, which differs from the pre-branch reader on none), not about every possible page.

## Consequences

- A page answers the same (visibility, principal, human certification) before and after it is migrated. Recall is the one answer that changes by design: the 188 Episodes become `approved` and 109 aggregates become Briefs, so what is recalled changes at the migration, not because a reader differs.
- **Deleted once the vault is fully on vocabulary 3** (a small follow-up, not done here because both forms must read until the migration lands): the `human:` actor and its prefix rule (`Actor::Human`, `Actor::is_human`, `OkfBlock::is_human_verified`, the `human:<name>` label route in `Roster::resolve`, and the named exception in the parity test); the roster's vocabulary 2 `generators` section and `GeneratorFacts`; the vocabulary 2 list form of `working_types`; the `INVALID_STAMP` warning branch and the `is_v3()` severity and status branches in `vault validate`; the `Status` enum's role for working pages; and, for working pages, the `public:` reading under `Rules::Visibility` (the conflict and `public`-without-`visibility` cases). Knowledge pages keep `public: true` under vocabulary 3, which is why `visibility::read` already takes `Rules` and stays.
- **Known limits, stated.** (a) The flat legacy fallback (`FileService` and the markdown-mirror page handler) has no vault layout and no vocabulary, so it reads `public: true` alone: it never publishes on `visibility`, but a v3 working page that still says `public: true` beside a non-public `visibility` would be admitted there, where ontomark would keep it private. The corpus sync, which has both, applies the vocabulary 3 rule. (b) `public: true` with no `visibility` under vocabulary 3 is not public here and ontomark does not publish it either; it is not reported as a `Problem`. (c) **Roster, stamps and the class-marker label (review V5, V6, V7), done.** A roster file that exists but will not parse is an error (`Roster::load`; `vault validate`, `gate` and `build` stop on it), never an empty roster; a file that does not exist is an empty roster, so no `did:nostr:` key resolves and none certifies. The corpus sync does not read the roster, so there is nothing to stop there. Under vocabulary 3 the `human:<anything>` spelling certifies nobody (`Roster::under_vocabulary`, applied by `validate_with`) and `validate` reports it as an `INVALID_STAMP` error (ruling 2); under vocabulary 2 the prefix rule stands. A `verified` stamp certifies only with an RFC 3339 `at` (milliseconds allowed, as the corpus writes them). `npub_to_hex` refuses a Bech32m checksum: the `bech32` crate's `decode` accepts both, so the checksum is checked explicitly (test `a_bech32m_checksum_is_refused`). `public_declared_false` feeds only `inclusion_reason`, a label, never the gate; a migrated `visibility: shared|private` page with a class marker keeps the ADR-2014 answers (graph-included, not publishable, "despite public false"), pinned by a test. The disagreement this paragraph once pinned (`knowledge/VcVerifiedNpub`) is closed: ontomark v0.10.0 agrees, see the re-vendoring note below.
- **Roster rule: only a principal's own keys carry its kind (review V4, fixed).** A key is human only if the roster lists it as a principal of `kind: human`: its canonical `did` or a key under its `also`. A generator (swarm, process, instrument) filed under or attributed to a principal resolves to that principal for attribution, but keeps its own kind and is **never** human, whatever principal it acts for and even if it states `kind: human`; a generator that states no kind is not human. So a page `verified` only by a swarm key is not certified, and the promotion state machine and every approver check (they all go through `Roster::is_human`) refuse it; the operator's canonical key and `also` keys, Fungible Token's included, still certify. Tests: `a_page_verified_only_by_a_swarm_key_is_not_certified`, `a_generator_filed_under_a_principal_acts_for_it_but_is_never_human`. The ontomark fixture holds no generator, so the vendored `golden.json` is unaffected; ontomark v0.10.0 applies the same rule under vocabulary 3 (its B1), so the two tools now agree on that case. **Trust boundary kept:** whoever can commit `ontology/attribution.yaml` decides who is human (they can mark any DID `kind: human` or list it under `also`); that is no more than vault write access already grants, because stamps are `asserted`, not signed. Owner review of that file remains advisable (the implementer's suggestion).
- `visionclaw-domain` now depends on `vault-core` (and so on `ontomark-parse`, `rdfs-certificate` and `bech32`): the cost of one reading.
- **Not done here.** The corpus sync does not yet honour authored clocks (a page that says `corrected`, `withdrawn` or `world-changed`); see the scope below. Replacing `vault-core`'s header code with ontomark's parser needs a released, light crate; today nothing of the kind is published (visionGraph's v3 reader is unreleased and lives in `ontomark-compile`, which brings the reasoner and takes ontomark's own `Page` types).
- The root crate type-checks with the feature set the temporal work used (see Verification); its test targets cannot be compiled in this container.

## Scope: the corpus sync honouring authored clocks (planned ADR-2022 P2 amendment; not implemented)

The sync (`corpus_history::plan_history`) closes every open version whose triple has left the public projection, with a valid-time closure at the sync instant. Authored clocks would add, per page: `corrected` or `withdrawn` produces a recorded-time closure through `build_correction`; `world-changed` or a deprecated-but-public page's `valid-to` produces a valid-time closure at that `valid-to`; knowledge `merged` and `renamed` close nothing. It needs the page header to reach the planner (today `public_subgraph` sees only node metadata), a `(page, version)` link, and tests on the vector cases; the design, files and risks are in the delivery report and are to be written into ADR-2022's amendment when the work is scheduled.
