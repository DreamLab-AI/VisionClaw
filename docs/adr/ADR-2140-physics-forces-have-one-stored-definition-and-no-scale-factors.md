# ADR-2140 — Physics forces have one stored definition, applied as stored

## Context
- The semantic-force kernels were never launched: their FFI entry points were no-op C stubs, the parameters lived in a separate actor with its own all-enabled defaults, and CPU twins mutated `GraphData` behind a `gpu_available()` check. `gpu_available()` reported the cargo feature, not the link.
- Values could be changed without reaching the GPU: the settings gate compared a hand-kept field list (ten GPU fields were dropped while the PUT answered 200), the route and the actor validated differently, the shallow physics merge replaced a nested patch's whole group, and an "advanced weights" path multiplied stored values in place on every call.
- Measured (9.5k nodes, live field median |f| 36, p95 50): at their old defaults the DAG force had median 91 / p95 351 and collision median 56, enough to flatten the layout.

## Decision
1. **Every physics parameter has one stored definition**: the central physics settings document (`physics.*`; the semantic forces are `physics.semantic`). Everything else derives from it. No actor, endpoint or client holds a second copy, and no value is built from `Default` downstream.
2. **A value is applied exactly as stored.** There is no scale factor, multiplier, clamp or cap between the store and the GPU. What bounds a force is its validated range in the schema.
3. **One write path**: client control → settings store (deep-merged, validated once by the same validator the actor uses, finiteness checked explicitly) → `SimulationParams` → GPU. The idempotency gate compares everything the GPU would receive differently, including the semantic group.
4. **Each force has its own `enabled` flag in the store.** There is no master multiplier. A failure to set a force up (metadata, PTX, upload) is an error in the log and leaves that force off for the graph; there is no CPU fallback.
5. **The group's controls are described once**: the Rust field table emits `semantic-forces-fields.json`; the web registry, the client defaults and the XR HUD load it; tests pin each copy to the Rust definition and every slider range to the validator's accepted range.
6. **Defaults are calibrated by measurement** and recorded where they are defined. Forces that work by pulling nodes onto planes (`dag`, `maturityLayout`) ship off.

## Consequences
- Removed: `SemanticForcesActor` and its supervision, `Configure{DAG,TypeClustering,Collision}`, the stub FFI bridge and semantic stubs, the CPU twins, the quality-gate copies of the DAG/type-cluster parameters, `UpdateAdvancedParams` and its baseline*weight mechanism.
- A control cannot silently do nothing: the web client nests semantic paths into the PUT, and the server deep-merges, so one slider changes one field.
- Every force costs GPU time (each O(n²) kernel ≈ 1–1.7 ms at 9.5k nodes); disabling a force in the store removes it from the step.

## Layout lock
The host writes the device config as flat 32-bit word images. `semantic_forces.cu` carries `static_assert`s for every size and offset the image assumes (140 bytes; per-group offsets; the 4108-byte relationship table), so a layout the compiler does not give fails the build. The group's types reject unknown keys (`deny_unknown_fields`): a misspelt or snake_case key is a 400, never a quiet no-op.

**What changed, with the behaviour each preserved:**
- *Field and migration.* `PhysicsSettings.layout_mode` (`layoutMode`, alias `layout_mode`, default `forceDirected`; `physics_config.rs`). All seven strings map to distinct modes (`LayoutMode::from_quality_gate_str`, `layout.rs`); `temporal` has no string. Write is strict: `merge_physics_patch` refuses an unknown or non-string mode with a 400 before the merge, and stores the serde name for either vocabulary. Load is lenient: the field deserialiser logs and defaults, so one bad value does not drop the document. A stored document without the field takes the mode from the stored `quality_gates.layoutMode` at boot (`migrate_layout_mode`, `physics_restore.rs`, used by `app_state.rs` and `load_saved_physics`) and is written back once; an unknown string is a logged default.
- *Endpoint.* `POST /api/layout/mode` applies `{"layoutMode": …}` through `apply_physics_patch` (`layout_handler.rs`). It now needs an authenticated user (an anonymous viewer gets a 401 on mode changes and loses the spectral and temporal one-shot placement; the desktop client signs NIP-98 when logged in, the XR client already signs) and carries `RateLimit::per_minute(60)`, like `/sssp/toggle`. A legacy `PUT /api/settings/quality-gates` that names a mode is forwarded through the same path, and `GET` reports the quality-gate string from the stored mode.
- *Removed from the actor:* the `SetLayoutMode` message and handler (it also cleared the opposing bias term on a switch), the preserve-override in `UpdateSimulationParams`, `fill_mode_defaults` and its three tests, and the duplicate defaults in `SetRadialLayout` (now the domain constants; it still primes the shells on the device only, as an action, whichever mode is stored).
- *Removed override blocks:* the quality-gate propagation overlay (`settings_routes.rs`, formerly `:1224-1226` and its `type-clustering` arm) and `propagate_physics_to_gpu_with_layout` (`settings_handler/physics.rs`, formerly `:102`, dead).
- *Two seams found in review, both corrected after the second review (R13).* `reset_layout` sent `PhysicsSettings::default()` and so reset the device mode, which the actor's preserve-override used to prevent; it now keeps the mode of the stored document (`reset_document_for`, tested with a stored non-default mode). The stored `physics` row is now the single source of truth, as decision 1 requires, in two places. (a) At startup the settings actor loads through `load_all_settings`, which overlays the `physics` row (with `migrate_layout_mode`) onto the snapshot's physics wholesale (`seed_physics_from_blob`, `sqlite_settings_repository.rs`); the row is read by key, so a legacy `physics.*` leaf cannot leak into it, and a frozen `visualisation.graphs.knowledge.physics.*` leaf can never win. That makes the row the merge base of `apply_physics_patch` at startup (see the follow-ups below for the two cases where they can diverge). (b) `stored_physics()` (`settings_routes.rs`) reads the same row first, so the no-op skip in `POST /layout/mode`, `GET /layout/modes`, `GET /layout/status`, `/sssp/status`, the quality-gate echo and `reset_layout` all read the document the device was given at boot. The first version of this seam (`fill_layout_mode`, which filled only the mode and only when a leaf object existed) was a no-op against the live store, which holds the `physics` row and no leaves: after a restart the snapshot held defaults and the first partial write merged onto them. It is deleted. The other `UpdateSimulationParams` senders that build from `Default` (`ActixPhysicsAdapter`, `actix_physics_adapter.rs:322/:454`) are reachable (`POST /api/physics/start` and `/parameters` are mounted through `PhysicsService`, `main.rs:855`, `:1172`) but cannot reach the device: `initialize` starts a private `PhysicsOrchestratorActor::new(SimulationParams::default(), None, …)` whose `gpu_compute_addr` is `None`, and nothing sends that actor `StoreGPUComputeAddress`, so its forward (`physics_orchestrator_actor.rs:1380`) never fires. The no-op skip's safety depends on that.
- *The quality-gate echo.* `qualityGates.layoutMode` on the wire is a read-only echo, and a client that GETs the gates, flips one toggle and PUTs the object back sends it along. The handler forwards a `layoutMode` to the physics write only when it differs from what the stored document would echo (`layout_mode_to_forward`); the echo itself writes nothing, so a gate toggle can no longer reset `temporal` (which has no quality-gate string, so its echo is the persisted string) or any other mode, and no longer costs a physics write and broadcast. The client's `updateQualityGates` also drops the echoed field from its merged body.
- *Unmounted write path.* `settings_handler` (`api_handler/mod.rs:122` is commented out) still carries a physics write path, `propagate_physics_to_gpu` (`settings_handler/physics.rs`, called from `physics.rs` and `enhanced.rs`), that builds device parameters without reading the stored mode. It is unmounted and so unreachable. It would reset the layout mode if it were ever remounted. It is not deleted in this change.
- *Spectral and Temporal* are CPU one-shot placements by the layout handler. The stored field says "place once"; no GPU term reads the mode (the kernel only carries the field in `SimParams`), so the store and the device cannot disagree. (The stored `temporal` mode used to be clobbered by a quality-gate PUT; the echo rule above closes that.)

**Booleans and floors, exactly (floors: owner-confirmed 2026-11-01).** The ruling's "0 = default" does not cover a boolean, so booleans are never touched by a mode: `ssspEnabled` is applied as stored in every mode (a document without it loads `true`), and no mode forces a toggle. The three numeric floors the overlay applied are now stored-0 defaults. This extends ruling 1, which names only the four bias fields, to three more fields; **the owner confirmed all three on 2026-11-01**, as the same rule as ruling 1. Removing the `max()` between store and device is required by decision 2 either way. The `typeClustering` cluster strength is nearly forced by ruling 2 (otherwise that mode equals `forceDirected` bar a discriminant no kernel reads); the centre-gravity and SSSP-alpha floors only act on a stored 0 and are inert for default documents. The cost: in the DAG modes a user cannot switch centring or SSSP strength fully off with 0 (0.0001 or `ssspEnabled=false` do), and in `typeClustering` cluster strength cannot be 0. The extension is: in `hierarchical`, `radial` and `dagLeftRight`, `centerGravityK <= 0` → 0.1 and `ssspAlpha <= 0` → 0.5; in `typeClustering`, `clusterStrength <= 0` → 0.01. A positive stored value is applied as stored. `/sssp/status` reports `enabled` and `alpha` from the same conversion, so it reports what the device holds.

**Behaviour changes to accept (the rest is unchanged):**
1. A stored `ssspEnabled=false` is obeyed in DAG modes (the overlay used to force SSSP on).
2. A stored positive `centerGravityK` below 0.1, `ssspAlpha` below 0.5 or `clusterStrength` below 0.01 is obeyed in its mode; the overlay used to raise it. Default documents are unaffected (0.2, 1.5, and 0 → 0.01).
3. No opposing term is cleared on a switch: an explicit positive `layerBiasK` stays in `radial`. Default documents have 0 there.
4. The overlay used to apply only after a quality-gate PUT and was dropped by the next physics write; the mode and its defaults now hold on every write and at boot. A document that stored `qualityGates.layoutMode` but no `physics.layoutMode` boots into that mode instead of `forceDirected`.
5. The direct enum names `hierarchical` and `radial` now carry the DAG defaults (before, only the `dag-*` strings did); the client only ever sent the strings.

## Follow-ups from the third review (R14, 2026-11-01)

Not reachable on the live store (one full `physics` row, written whole by `AppState::new` and `apply_physics_patch`), and no worse than `main` in either case; recorded so `complete` stays honest.

- **N1, Medium.** `load_all_settings` deserialises the leaf tree (`sqlite_settings_repository.rs:697`, `?`) before `seed_physics_from_blob` (`:708`). A malformed `physics` row or a partial older-schema leaf set fails that step, so the seed never runs and the actor keeps `AppFullSettings::new()` defaults, which is `main`'s behaviour. The seed's doc comment ("the load never fails because of it") is therefore false on that path. Fix: seed a defaults instance in the `Err` branch (or strip `physics` from `root` before the tree deserialise), with a `load_all_settings`-level test for a malformed row and for a readable row plus a partial leaf set.
- **N2, Low.** `apply_physics_patch` updates the actor first and persists the row last, warning on failure. Readers now read the row while the merge base is the actor, so a failed persist leaves the device and actor on new values and the readers and the next boot on old ones. Pre-existing and unrun: whole-snapshot read-modify-write handlers (`update_rendering_settings`, `constraints_handler.rs:73`) can race a physics patch. Fix: merge onto `stored_physics()`, persist before the actor update, and return 500 on a failed persist.
- **N5, Info.** With `temporal` stored, a deliberate quality-gate PUT of the echoed mode is indistinguishable from the echo and is dropped. No live caller sets `qualityGates.layoutMode` deliberately.
