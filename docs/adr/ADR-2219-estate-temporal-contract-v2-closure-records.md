# ADR-2219 — Temporal contract v2: versions never carry an end; closing is a closure record

## Context

Contract `estate-temporal-v1` closed a version by adding a bare `dl:validTo` quad to it. That quad has no recorded time of its own, so a knowledge-cut query (`recorded_as_of`) could not tell when the close became known. Measured on the live store: 158,635 corpus versions were opened by the sync of 2026-11-19T13:26:13Z and 15 were closed by the sync of 2026-11-20T08:55:06Z. A query for 2026-11-21 as the store knew it at 2026-11-19T20:00Z returned **158,620**, applying a close that had not yet been recorded; the correct answer is **158,635**. v1 also had no way to withdraw a version as wrong (a correction) and gave a re-assertion the same IRI as the version it re-asserted.

## Decision

1. **A version never carries an end.** It is a `prov:Entity` with `rdf:subject/predicate/object`, `temporal:validFrom` and `temporal:recordedFrom` (`xsd:dateTimeStamp`), `prov:wasGeneratedBy` and `prov:wasAttributedTo`. `dl:validTo` is retired from the provenance graph, and so is `dl:validFrom` on versions.
2. **A closure record closes it.** `<closure> a dl:Closure; dl:closesVersion <version>; dl:closes <clock>…; dl:validUntil …` (present iff valid time is closed); its own `prov:generatedAtTime` (when the close was recorded), `prov:wasGeneratedBy`, `prov:wasAttributedTo`, optional `dl:reason`. A closure closes at least one clock, is not a version, and is never itself closed. The two clock values are `memory:ValidTime` (the world changed) and `memory:RecordedTime` (the version was never true: a correction).
3. **One state rule, one SPARQL form.** A version is in `state(t, r)` iff recorded by `r`, valid from `t`, with no `RecordedTime` closure recorded by `r` and no `ValidTime` closure recorded by `r` whose `validUntil <= t`. Without `r` every closure applies; several closures each exclude independently and the reported `validTo` is the earliest applicable end. The reader (`build_state_at_sparql`, `build_state_at_subjects_sparql`) uses two `MINUS` groups and an aggregating sub-select for the end, with separate variables per group. The pure `state_at` implements the same rule.
4. **Identity.** The version IRI hashes `{subject, predicate, object, validFrom, generatedAt}` under the agent's scope segment, so a re-assertion or reinstating version recorded later never collides with an earlier one; a wrong correction is undone by asserting a new version. A closure IRI hashes `{version, clocks, validUntil, recordedAt}`. Both match agentbox `uris.js` byte for byte (goldens generated by running `uris.js`). Every existing version IRI therefore changes at the refit.
5. **Writers.** `build_closure` (valid-time or recorded-time close, validated: a closure with no clock, a valid-time closure with no end, an end without valid time, an end not after `validFrom`, or a close recorded before its version is rejected) and `build_correction` (recorded-time close with an optional replacement). The corpus sync writes its closes as closure records linked to its own activity and agent; "open" means "has no closure". Two syncs cannot share a second (`monotonic_sync_instant`). `build_retraction_update`, `asserted_delete`, the duplicate `state_at_sparql`, `AssertionInput.valid_to` and the legacy activity-prefix reader are deleted.
6. **Stored timestamps are canonical** (UTC, whole seconds, `Z`): `build_activity_quads` writes `prov:startedAtTime`/`generatedAtTime` through `wire_timestamp`. The `inference_run_id` hash input is unchanged.
7. **Refit, offline.** `temporal-refit <store>` is a one-off tool (dry run by default). It refuses on anything it cannot match, replays the corpus history through the production `plan_history` into a scratch store at the true sync instants, verifies it, and with `--apply` replaces the old corpus-owned history in one transaction. It writes no marker predicate and no ledger row: **a refit is recorded in this ADR, not in the data.** The tool is to be removed from the tree once no pre-refit backup remains.
8. **Guard, read-only.** If the provenance graph holds a `dl:validTo` quad, or `dl:validFrom` on a version, `AppState` logs an error at boot and the corpus sync records no history (with the reason in its report) until the refit has run. Nothing is written.
9. **Append-only is restated** (ADR-2016, reworded): append-only *in operation*, with no runtime delete path, and exactly two named exceptions: an operator-approved contract refit recorded in an ADR, and ADR-2102 erasure.

Out of the contract: federation tombstones (cache eviction of received copies, not a temporal fact) and erasure (ADR-2102). A page left `public: true` but `status: deprecated` receives no close; that is documented behaviour, not an oversight.

## Consequences

- **The knowledge cut is correct** and a correction is expressible. Cost: every version IRI changes once, at the refit; anything that stored a version IRI would lose it (no consumer in this repository does, by grep; agentbox was not searched).
- **Old-binary hazard.** Applied migrations are not edited (ADR-101 D5), so nothing stops a pre-v2 binary booting against a refit store. By reading the code (not run), it would find no open versions (it looks for `dl:validFrom`) and its next sync would open every public triple again, in the old form, beside the v2 history. Do not run a pre-v2 build (for example `wt/abs-neon`) on a refit volume. Rollback is **restoring the pre-refit checkpoint**; keep one outside the volume (`KEEP = 2` in `visionclaw-backup` prunes the in-volume ones). A v2 binary on a restored pre-refit store is held off only partly: the boot guard disables the **corpus sync's** history, but other writers (governed decisions) would still write v2-form versions beside the old form, and the refit tool then refuses the store as "mixed forms". **Never boot a v2 binary on an unrefitted or restored store; refit first.** (If that proves too brittle, the alternative is for the refit's preflight to ignore non-corpus versions already in v2 form; not done.)
- **Cost of the reader.** Measured here on 20,000 versions and 1,000 closures: the `MINUS` form 0.22 to 0.28 s; `FILTER NOT EXISTS` 1.3 to 1.5 s; `OPTIONAL` with `GROUP BY` 13.9 s. On the 158,635-version store the earlier review measured 1.6 s, 12 s and 299 s. The conformance test keeps the first from regressing to the second.
- **The graph is not tamper-evident** (it never was): it records history under the current contract and is replaced only by a refit.
- **Not done here.** (a) The lifecycle of decision versions (`dl:DecisionRecord`), which no code ever closes, is an **open owner decision**; this ADR does not change it. (b) Corrections to the corpus reach history only through the sync reading an authored page marker (planned, ADR-VG-010 §3); until then `build_correction` has no production caller and there is no governed API for corrections (PRD-022). A recorded close on a corpus version whose triple is still in the vault would be reopened by the next sync as "true again from now", which is why the marker path is the only sound one. (c) memory-ontology's `temporal:TemporalAssertion` reifies with `rdf:reifies` (RDF 1.2); Oxigraph 0.4 has no triple terms, so versions keep `rdf:subject/predicate/object`: property IRIs are shared, shape conformance is not claimed.

## Refit of the live store — pending the operator

The code and tool are on branch `feat/temporal-contract-v2`; **the live store has not been refitted and nothing has been deployed.** Procedure, application stopped, from the host shell:

1. Copy a checkpoint: `cp -a <data>/oxigraph <scratch>/oxigraph-refit-trial` and keep one pre-refit checkpoint outside the volume.
2. Dry run on the copy (never boot the application on it): `temporal-refit <scratch>/oxigraph-refit-trial --expect-versions 158635 --expect-closes 15 --expect-other-activities 209`. It must end `DRY RUN` with no `[FAIL]` line and report 158,635 versions, 15 bare closes, two corpus-sync activities (2026-11-19T13:26:13Z, 2026-11-20T08:55:06Z) and, for a generated cut between the two syncs, 158,635 with the later closes not applied and 158,620 without a cut. (The literal case t = 2026-11-21, r = 2026-11-19T20:00Z is asserted only by the ignored production-size rehearsal test; the tool's own check uses the equivalent cut r = the midpoint of the two syncs.)
3. Apply to the copy (`--apply`), confirm `REFIT COMPLETE`, then run again to see `nothing to do`.
4. Only then repeat steps 2 and 3 on the live volume, and start the v2 binary. `--apply` holds its transaction (about 2.5 million quad operations at the live size) in memory: run the copy trial on the same host first and watch its resident memory.

**Record here when done:** date, tool commit, store, before and after counts, and the verify output. (Rehearsed so far only on synthetic stores, including one at the live size: 158,635 versions and 15 closes replay and verify in 41 s in memory.)
