## 1. VisionClaw presence today

**Room identity.** `RoomId` = `urn:visionclaw:room:sha256-12-<12 hex>`; `RoomId::parse` only checks prefix, `sha256-12-` and 12 hex chars (`P/crates/visionclaw-xr-presence/src/types.rs:39-62`). It does NOT check the hex is actually a SHA-256 of anything. The room is a free string the client supplies in the `auth` frame (`P/src/handlers/presence_handler.rs:104-105, 273`). XR client default is a constant `urn:visionclaw:room:sha256-12-deadbeefcafe` (`P/xr-client/scripts/graph_scene.gd:83`), overridable via `XR_ROOM_URN` (`:1520`).
- Taxonomy: `room` row, "unscoped XR presence room", minter `room()` at `src/uri/mod.rs:308` (`P/docs/IDENTIFIER-taxonomy.md:52`). Doc admits room URNs are test-only, never minted in production (`:67-70`). There is also a `urn:visionclaw:group:<team>#members` kind (`:51`, minter `group_members()` `:298`) — a team-membership ref; the nearest existing slot for a NIP-29 group id, but it is team-scoped, not relay-scoped.
- Wire hash: `RoomId::wire_hash()` is a 16-byte double-FNV-1a of the URN string (`types.rs:~58-77`), NOT a sha256. Broadcast envelope carries only `u32 room_id` (`P/docs/PROTOCOL-registry.md:153`; `presence_actor.rs:49`). A federated room id needs a defined mapping into both (collision risk, see table).

**Auth / who can join.** `/ws/presence` (`P/src/main.rs:1119`, state at `:888`): server sends 32-byte CSPRNG nonce + ts; client returns `auth{did, signature, room_id, metadata, ts?}` where the signature is BIP-340 Schnorr over `(nonce||ts)` — bespoke challenge, NOT NIP-98 and NOT NIP-42 (`presence_handler.rs:191-250`; `P/src/services/nostr_identity_verifier.rs:35`; trait `IdentityVerifier` at `P/crates/visionclaw-xr-presence/src/ports/mod.rs:19-21`). Checks: ±30 s ts skew (`:61`), signature, did == signed key, replay LRU on nonce (`:256-270`). Then `RoomId::parse` and join. **Any authenticated did:nostr can join ANY room id; there is no per-room authorisation, member list or cap** (`presence_handler.rs:273-330`; `presence_actor.rs:664-680` only rejects duplicate DID). Registry is an in-memory `DashMap<room-urn, Addr<PresenceActor>>`; actors self-stop when empty (`presence_handler.rs:~283-296`).
- Aggregate invariants (`P/crates/visionclaw-xr-presence/src/room.rs:17-21`): I-PR01 one DID ↔ one avatar per room (`:42-49`, `DuplicateDid`); I-AV01 strictly monotonic pose timestamps (enforced in `validate.rs`/actor ingest, `presence_actor.rs:751`).
- A `WellFormedOnlyVerifier` stub exists (`nostr_identity_verifier.rs:~118`) — must never be wired in prod.
- **No Nostr group membership concept exists in presence.** Only Nostr-ish room-adjacent thing: `group_members` URN kind. Grep for `nip-29|39000|9021` in `P/src,crates,docs` finds only the bridge (§2).

**Where a NIP-29 membership check plugs in.** Single natural seam: between verified DID and `registry.entry(...)` / `JoinRoom` in `handle_auth` (`presence_handler.rs:~270-300`, after `verified` + replay check, before actor spawn). Hexagonal option consistent with the crate: add a `RoomAdmission` port next to `IdentityVerifier` in `ports/mod.rs` (`fn admit(&self, did:&Did, room:&RoomId) -> Result<(),RoomError>`), injected through `PresenceHandlerState` (`main.rs:888`). Backing impl: cache of relay-signed kind 39002 member lists (or a REQ with NIP-42 AUTH) for the group the room maps to. `JoinRejection` (`presence_actor.rs:166`) needs a `NotMember` variant; `RoomError` (`error.rs`) likewise. Also `Did::pubkey_hex()` already exists for the p-tag compare.

Review trigger names "a fourth body joining the separated layout" — **adding a room/space body requires amending ADR-2135** and the fixture.
- So today the XR scene already hosts ONE scene containing THREE bodies (KG, ontology, memory cloud) + agents, all in a single Godot `GraphScene` (`xr-client/scripts/graph_scene.gd`, booted by `xr_boot.gd:53-56`, single OpenXR interface init `xr_boot.gd:10`). It is not three XR containers; it is three bodies placed by one layout inside one origin. There is no OpenXR spatial-entity/anchor/container API use in xr-client (greps on `xr_boot.gd`; `plane_manager.gd`/`spatial_environment.gd` exist — not inspected in depth, worth a look by the OpenXR worker).
- Backend binding is **single**: one `_graph_ws_url` (`graph_scene.gd:166`), from `XR_BACKEND_WS` + `XR_BACKEND_MODE` (`:1512-1534`); `_switch_backend(mode)` (`:909`) tears down the old socket/state and rebinds (XR-client.md ~`:950-975`). - Codescape: separate repo/submodule `P/codescape/` (DreamLab-AI/codescape), own Cargo workspace (crates: codescape-collab, -ingest, -layout, -model, -server), serves on **:4100** (hook-ingest :4101 internal-only, bearer); reachable via dev nginx at `http://<host>:3001/codescape/` (ADR-2143 A4, `:181-194`); compose binds :4100 to 127.0.0.1 by default (`docker-compose.unified.yml:477-482`); NIP-98/TLS allowlist is P6, NOT done — :4100 has `auth: open` until then (`ADR-2143:155,166`). Implementation status partial (P0 done, P2-P6 not). Isolation I9/I10 forbids any path dependency root↔codescape (`AGENTS.md`; `codescape-server/tests/isolation.rs`). Hence a room-binding crate shared with Codescape would have to be published to crates.io (like `visionclaw-wire`), not path-linked.
- Operator trial (one OpenXR spatial container per graph — KG, ontology, codescape): current architecture = one GraphScene, one backend. Needs (a) a scene-graph root per container (Node3D under XROrigin or an OpenXR anchor), (b) N concurrent graph sockets (today `_graph_ws_url` scalar), (c) tri-layout to be demoted from "the" layout to a per-container option.
