## Headline findings
1. **There is no Neo4j.** The lead's brief says Neo4j; the code says otherwise. Neo4j is "100% removed", the store of record is embedded Oxigraph plus SQLite (V `docs/DATA-authority-erasure.md:44-51`; V `docs/BASELINE-architecture.md:321-323`: "No networked graph DB").
2. **No node or edge carries a source/origin node field.** The only provenance-like fields are `owner_pubkey` (string in the `metadata` map) and `public` (V `src/actors/graph_state_actor.rs:182-193`). Federation provenance would be new.
3. **Wire ids are per-server, ephemeral and not federable as-is.** Two sources collide. The only safe pattern today is ADR-2159's one connection and one store per source (V `ADR-2024:6-30`).
4. **Erasure/retraction semantics for a remote node do not exist.** There is no 410/Gone/retract/tombstone mechanism in docs or `src` (V grep, no hits). The doc's own largest erasure hole is an unreversed tombstone (V `DATA-authority-erasure.md:87-91`).
5. **Codescape is the right precedent for the transport and the wrong one for trust.** It proves the "second producer of the frozen wire" model but is unauthenticated until its P6 (V `docs/PROTOCOL-registry.md:219-221`).

## Q1 Graph sourcing and provenance
- **Knowledge graph.** Authored content = Obsidian vault markdown with `public: true`/`owl-class` frontmatter, ingested by `CorpusSource` (ADR-2114), via `src/bin/sync_corpus.rs` and `src/services/file_service.rs`; ownership gate ADR-2040 (V `DATA-authority-erasure.md:40` ownership-matrix row 1). GitHub is upstream; the Oxigraph `GRAPH_KNOWLEDGE` projection is regenerated by a sync run, never hand-edited (V (§Conflict resolution)).
- **Ontology graph.** Oxigraph named graphs `GRAPH_ONTOLOGY`, `GRAPH_ONTOLOGY_INFERRED`, `GRAPH_KNOWLEDGE`, `GRAPH_AGENT`, `GRAPH_SHAPES`, `GRAPH_PROVENANCE` (V `crates/visionclaw-adapters/src/oxigraph_ontology_repository.rs:46-55`, quoted at `DATA-authority-erasure.md:49-51`). `:assert` is authored; `:inferred` is Whelk-derived and rebuilt each reasoner run (V `DATA-authority-erasure.md:65-70`).
- **Loom.** The Ontology Loom is the vault's reasoner/HTTP façade for the corpus, per the workspace notes. In this repo the ontology data reaches the pod by `services::ontology_pull`, which fetches a rolling GitHub release `ontology-latest` and publishes it atomically into the in-process Solid pod under `/public/ontology/` (V `src/services/ontology_pull.rs:1-24`; V `docs/BASELINE-architecture.md:381`). Pods are therefore a *publication* surface for ontology resources, not the live graph store (I, from those two cites).
- **Live in-memory owner.** `GraphStateActor` is "the only writer" of the in-memory `GraphData` and persists add/remove to Oxigraph fire-and-forget (V `src/actors/graph_state_actor.rs:67`, `:131`, `:376-411`). Its compact ids map back to persistent ids via `compact_to_persistent` (V `:93`, `:206`).
- **Node/edge fields.** `Node` has `id: u32`, `metadata_id`, `owl_class_iri`, free-form `metadata: HashMap<String,String>` (V `crates/visionclaw-domain/src/models/node.rs:34-76`). `Edge` has `id`, `source: u32`, `target: u32`, `edge_type`, `owl_property_iri`, `metadata` (V `crates/visionclaw-domain/src/models/edge.rs:175-186`).
- **Provenance/origin.** None typed. `owner_pubkey` and `public` live only as metadata keys and drive the visibility filter (V `graph_state_actor.rs:182-193`; V `crates/visionclaw-domain/src/utils/visibility_filter.rs:12`, `:56-58`). The `urn:visionclaw:kg:<hex-pubkey>:<sha256-12>` kind is owner-scoped and content-addressed (V `src/uri/mod.rs:57-58`, minted at `:242`, `:255`) but the `Node` struct has no urn field; `metadata_id` is the closest (I). PROV-O activity records live in `GRAPH_PROVENANCE`, append-only (V `DATA-authority-erasure.md` ownership row 'Event journal', Invariant 3 `:146`).

## Q2 Node identity on the wire
- **Layout.** V3 id `@0` is u32: bits 0-25 id (`NODE_ID_MASK=0x03FF_FFFF`), flags `AGENT 0x8000_0000`, `KNOWLEDGE 0x4000_0000`, ontology subtypes bits 26-28 (V `docs/PROTOCOL-registry.md:96-98`). Bit 29 is unallocated (V `:201-203`).
- **Allocation.** Ids come from a process-global `AtomicU32` starting at 1 (V `crates/visionclaw-domain/src/models/node.rs:7`, `:87`). ADR-2024: wire id is "ephemeral and render-only, never durable" (V `ADR-2024-wire-node-id-26bit.md:25-33`).
- **Collision.** Two servers' ids overlap in 1..N; nothing on the wire says which source an id belongs to (I; follows from the above). A shared store would conflate them. ADR-2159 rejects "one shared render store keyed by source" for exactly this reason (V `ADR-2159:50-51`).
- **Overflow.** Over-range ids are masked silently in release (`debug_assert!` + log) (V `IDENTIFIER-taxonomy.md` Invariant 6, `:212-217`; V `ADR-2024:34-37`). Merging two id spaces into one 26-bit space would risk this.
- **Codescape today.** Separate process, separate socket, its own 26-bit *interned* ids, never hashed, never reused in an epoch, no flag bits for code nodes, `AGENT` bit for actors (V `PROTOCOL-registry.md:201-203`; V `docs/XR-client.md:937-946`). It avoids collision purely by being a different connection with a different client store, not by namespacing (I).
- **Invariants that constrain adding foreign nodes** (`PROTOCOL-registry.md`):
  - byte 0 is the version tag; unknown tags are rejected (V Invariants, `:325`); V3 record is exactly 52 bytes, compile-time asserted (V `:326-329`); `NODE_ID_MASK` fixed, flag bits stripped before map lookups (V `:330`);
  - tag allocation only in this registry, per socket (V `:332`); additive envelopes only, "new per-node data extends the record only by a new tag with a new length" (V `:274-276`).
  - Consequence: a source-id field cannot be added to the 52-byte record. Provenance must ride a new tag, a text frame, or the connection itself (I).
- **Delivery contract (ADR-2141).** Per-client, acknowledgement-driven chunks, absolute positions, no deltas (V `PROTOCOL-registry.md` Version-negotiation item 6 (~`:283`)). A foreign source can be a second producer honouring `0x34` acks (V `:208-209`).

## Q3 Cross-graph edges
- **Today an edge is two u32 wire/compact ids in one `GraphData`** (V `edge.rs:177-180`). It cannot reference a node from another source; ids are meaningless across servers (I).
- **Durable identifiers.** `urn:visionclaw:*` has seven kinds: concept, kg, bead, execution, group, room, avatar (V `src/uri/mod.rs:54-69`). `kg` is owner-scoped, so a remote node is addressable as `urn:visionclaw:kg:<remote-owner-hex>:<addr>` without a new kind (I). `concept:<domain>:<slug>` is the shared-ontology kind and fits ontology bridging (I).
- **No node-host element.** The URN carries *owner*, not *home server*. Resolving a URN to a host needs a directory (DID document / relay / pod), which is not present (I).
- **Federation precedent.** `cross_from_agentbox` is a *closed kind-map*; unmapped kinds return `None`, never a synthetic id (V `src/uri/mod.rs:809`; V `ADR-2025:19-34`). `UrnCrossing{agentbox_urn, visionclaw_id, owner_did}` records both ends (V `uri/mod.rs:772-779`). ADR-2072 extends the map to beads. This is the template: a remote-node mapping should also be closed, fail to `None`, and store both ends (I).
- **Required for a local→remote edge** (all I):
  1. a stub/placeholder node *in the local store/volume*, keyed by the remote URN, with a local wire id; its remote id lives in a side table, never on the wire;
  2. the edge is then an ordinary local edge between local ids plus a `remoteUrn` marker (edge `metadata` can carry it, V `edge.rs:185`);
  3. the stub has no position authority: it is an anchor drawn at the volume boundary, not a simulated body.
  - The alternative, a world-space inter-volume link, is what ADR-2158 §6 already specifies for KG↔ontology bridges (V `ADR-2158:44`). The same mechanism extends to cross-source links with the stub being a client-side `(source, urn)` pair rather than a server node (I).
- **Ledger.** ADR-2021 (typed mint/parse; `parse` rejects `urn:ngm:*`, `parse_dual` accepts, V `IDENTIFIER-taxonomy.md` Invariant 7), ADR-2023 (sha256-12 content address, V Invariant 3). Both support federation joins by content address (I).

## Q4 Authority and erasure
- **Rule.** "One authoritative owner per class. No class may acquire a second write-master without an explicit conflict-resolution rule" (V `DATA-authority-erasure.md:149-150`).
- **Class of a remote node cached or rendered locally.** It is not a new owner class. It is a *derived projection* of the remote home node's authoritative class (authored content / graph projection), like `GRAPH_KNOWLEDGE` vs its source (V (§Conflict resolution): projection "regenerated, never hand-edited"). A local cache must therefore be read-only, disposable, and rebuilt from the home node (I).
- **Never write it into** `:assert`, `:inferred` or `:provenance`; only `:summary`/`:observed` accept writeback (V Invariant 2 `:144-145`). Do not store remote nodes in the local Oxigraph named graphs (I).
- **Visibility fail-closed** (Invariant 4, V `:148-149`). The remote home node must apply its own filter before serving; the local node cannot re-derive entitlement for data it did not own (I).
- **Erasure.** No estate-wide subject-erasure design exists (V `:92-96`); ADR-2102 is proposed (V `:191`). `GRAPH_PROVENANCE` is append-only (Invariant 3, V `:146-147`), so any provenance of a remote read needs redaction semantics that do not exist.
- **410/retraction.** None. grep for 410/Gone/retract/tombstone finds only the RuVector tombstone gap (V `:87-91`). A federation retraction message (remote says "node X withdrawn", cache must drop within TTL) is new design work (I). Minimum: do not persist remote data (render from memory only), so retraction = next snapshot omits it.
- **Replication.** Secondary-store fan-out is best-effort but must be observable (Invariant 6, V `:151-152`).

## Q5 Auth on the graph sockets
- **`/wss`.** Upgrade needs an `Origin` header (V `src/handlers/socket_flow_handler/http_handler.rs:120-139`), then a NIP-98 header carried via `Sec-WebSocket-Protocol` (V `:146-152`, `websocket_auth_header`), verified against the upgrade URL and method by the single-use validator (V `:143-145`, `:155-175`). Fallbacks: `Authorization: Bearer` (V `:178-185`); `?token=` is dev-only and compiled out of release (V `:187-198`; V `PROTOCOL-registry.md:305-308`). The registry table says "NIP-98 Bearer or ?token=" (V `:231`), which is stale against ADR-2058.
- **Anonymous.** Whether an unauthenticated release client can still open `/wss` is not established by what I read (I: `signed_user.is_none()` only gates the fallback; further code at `:200+` unread).
- **REST.** `RbacGate` role lattice Owner>Admin>Editor>Viewer on NIP-98 pubkeys (V `PROTOCOL-registry.md:244-246`). Anonymous safe-method reads only if `RBAC_PUBLIC_READS` (fail-closed default OFF, V `src/middleware/rbac_gate.rs:130-135`; compose default ON, V `docker-compose.unified.yml:132`). Mutations need `WriteGraph` (V `rbac_gate.rs:180-188`).
- **NIP-98 specifics.** ±60 s window plus single-use, process-local replay cache (V `PROTOCOL-registry.md:249-251`; V `SECURITY-profiles.md` Invariant 4 (~`:196-205`), Invariant 4: not replica-safe). A remote node signs with its own key.
- **Per-session filtering.** The visibility filter keeps `visibility='public' OR owner_pubkey=$session_pubkey` (V `visibility_filter.rs:12`). A remote node's DID would see only `public:true` nodes unless it equals the owner (I). That is already a usable **read-only federation default**: peer authenticates as did:nostr, gets public-only.
- **What serving a remote VisionClaw node needs** (I):
  1. identity = `did:nostr` from the NIP-98 pubkey (already how sessions bind);
  2. an **allowlist** (peer pubkeys) mapped to a new `Federated`/ReadOnly role. The role store already has precedence and fail-closed-to-Viewer (V `role_store.rs:188-199`, per `DATA-authority-erasure.md:71-72`). Codescape plans exactly this: "P6 NIP-98 pubkey allowlist on every route" (V `PROTOCOL-registry.md:221-223`);
  3. optionally a capability token (e.g. space/graph scope) for per-space grants; nothing exists today (I);
  4. the profile asserts before the listener binds (V `SECURITY-profiles.md:229-230`), and `RBAC_PUBLIC_READS=1` with `PUBKEY_VISIBILITY_FILTER=0` must never coexist (Invariant 5, V `:207-208`). A federation profile must be added to the named profiles (V `:101`).
  5. `/wss` is a *Browser* flow (Origin required). A node-to-node client has no browser Origin, so a server-to-server profile needs its own rule (I).

## Q6 Codescape as a precedent
- **Is it already a remote data space?** Functionally yes: a separate backend, separate process and ports 4100/4101, speaking the frozen wire, with its own store and ids (V `docs/BASELINE-architecture.md:331-332`, `PROTOCOL-registry.md:190-199`). Not remote in the network sense: loopback by default, and `0.0.0.0` publish is forbidden before P6 (V `ADR-2143:166`, `:155`).
- **What it gives us:**
  - **Emulation contract.** It emulates `/wss`: an `initialGraphLoad` text frame, then V5 frames with V3 records, `0x23` actions, `0x34` acks (V `docs/XR-client.md:940-947`). The XR client needs no wire change.
  - **`BackendCaps`.** `BackendCaps.for_mode` returns per-key capability dictionaries; unknown mode = VisionClaw (V `xr-client/scripts/backend_caps.gd:98-103`; V `XR-client.md:958-964`). `GraphScene._gate(cap,label)` guards request helpers (V `XR-client.md:960-963`). It is global per mode today; ADR-2159 §2 makes it per volume (V `ADR-2159:36`).
  - **`nodeDrag` refused.** `/wss` on Codescape honours only `authenticate`, `requestInitialData`, `ping`; `nodePin/Unpin/nodeDrag` are logged and dropped (V `XR-client.md:955-958`). ADR-2158 §5 turns this into a client-side refusal that is never sent (V `ADR-2158:41`).
  - **Knowledge routes 404** (V `PROTOCOL-registry.md:216-218`) — a model for an explicit "read-only space" route table.
  - **Isolation/tests.** Build-graph isolation test and wire pinned by `tests/codescape_wire.rs` (V `XR-client.md:989-990`; V `ADR-2143` I-table `:82-83`).
- **What it does not give us:**
  - **Auth.** `/wss` accepts the `authenticate` envelope but does not verify it; `"auth":"open"` until P6 (V `XR-client.md:987-988`; V `ADR-2143:155`). The visibility filter and entitlement rules govern `:4000` only (V `PROTOCOL-registry.md:221-223`).
  - **Foreign identity / URN.** Codescape ids are interned, with no URN per node on the wire (V `PROTOCOL-registry.md:201-203`).
  - **Multi-connection client.** Today `_switch_backend` is exclusive (V `ADR-2159:17`); ADR-2159 is unimplemented, and the tokio two-client precondition is untested (V `ADR-2159:21`, `:42`).
  - **Presence, mutation, physics write:** all refused. Fine for read-only; wrong for a *VisionClaw* peer that wants pins and drags.
  - **Two ops-heavy differences:** Codescape has no knowledge graph (`/api/memory-cloud/*` 404), but a remote VisionClaw node does. The `KNOWLEDGE`/ontology flag bits and visibility filter would apply to it (I).

## Q7 GPU and layout
- **Local physics.** Position broadcast path: GPU → `ForceComputeActor` → `PhysicsOrchestratorActor` → `ClientCoordinatorActor` → WebSocket (V `docs/BASELINE-architecture.md:323-325`; GPU tree `gpu_manager_actor.rs:57`, V `:183-192`). The simulation runs over the *local* `GraphStateActor` graph. Remote nodes would only be in it if inserted, and then they would be simulated as if local, which contradicts Q4's read-only projection (I).
- **Recommendation: do not run server physics on remote nodes.** The home node already holds a converged layout and streams absolute positions per client with acks (V `PROTOCOL-registry.md` Version-negotiation item 6 (~`:283`), ADR-2141). A remote volume should consume the home node's V5 stream and place it in the volume's local frame (I). This is also how Codescape works: the XR client treats each source's positions as authoritative for its volume (I; ADR-2159 §1 "never share a store or sequence", V `ADR-2159:31`).
- **Constraints.** `SimParams` is 212 bytes and statically asserted on both sides (V `GPU-wire-abi.md:243-244`, Invariant 1); `ENABLE_CONSTRAINTS` derives from `num_constraints > 0`, never from settings (V `:245-248`). Nothing in the GPU ABI carries a source tag, so cross-source springs would need a new constraint channel (I). Not recommended for v1.
- **Display projection.** ADR-2135's three bodies are placed by a server-side `display_projection` ("Triangle" mode) and an XR-side `TriangleFrame` (V `XR-client.md:11`; V `ADR-2135:253`). ADR-2158 §7 moves this to a client-side arrangement of volumes (V `ADR-2158:45`). A federated volume would be a fourth/fifth entry in that arrangement; the triangle's review trigger is already named (V `ADR-2135` frontmatter via `ADR-2158:47`).
- **Pins/drags on a remote space.** A pin writes to the *home* GPU. With an authenticated peer role that has `WriteGraph` on the home node, it would work (I), but remote writes by default should be refused as for Codescape.
- **Bounding.** Positions from the home node are in the home node's own coordinate scale; the fit rule maps the longest axis to 2.4 m (V `ADR-2158:20`, `graph_scene.gd:1920-1951`) and ADR-2158 §5 scales per volume, so no coordinate negotiation is needed (I).

## Q8 Ontology linking
- **Two ontologies by IRI.** Nodes carry `owl_class_iri`, edges `owl_property_iri` (V `node.rs:56`, `edge.rs:182-183`). The vault defines `owl:equivalentClass` through `defines-as` (V `crates/vault/src/validate.rs:1180`, `:1348`) and emits it in Turtle and proposals (V `crates/vault/src/propose.rs:1179`, `crates/vault/src/build/turtle.rs`).
- **Support in the Oxigraph path.** `owl:equivalentClass` is queried/loaded (V `oxigraph_ontology_repository.rs:568`, `:2397`) and `owl:sameAs` appears inside an associative-edge SPARQL filter (V `:2407`). `EdgeType` classification puts `owl:sameAs`/`equivalentClass` in the "hierarchical" bucket (V `edge.rs:234-235`). The Whelk engine skips mereological/associative assertions such as `sameAs` as TBox axioms (V `crates/visionclaw-adapters/src/whelk_inference_engine.rs:203`), so `sameAs` is not reasoned over (I).
- **So:** linking by IRI is natively expressible (`owl:equivalentClass` between classes, `owl:sameAs` assertions between individuals). There is no *alignment* mechanism: no import of a remote ontology, no mapping table, no cross-ontology reasoning. A federation would hold alignment triples in a local `GRAPH_ONTOLOGY` assertion by authored vault page, i.e. via `vault propose` (writes governed, ADR-2107; V `agentbox/AGENTS.md` canonical-runtime row for `[vault]`). Remote class IRIs must be published; `ontology_pull` and pod `/public/ontology/` already publish JSON-LD and Turtle (V `ontology_pull.rs:1-12`) (I).
- **Gotcha.** Code mints `urn:ngm:*` IRIs for ontology content while the taxonomy says `urn:visionclaw:*` (V `DATA-authority-erasure.md` 'Identifier grammars unreconciled'; V `IDENTIFIER-taxonomy.md` Invariant 7). Unreconciled, so cross-node IRI joins rely on convention (same bullet).

## Design implications for the lead (I)
1. **Per-source connection and store is correct** and is the only collision-proof design given frozen 26-bit ids (ADR-2159 §1).
2. **Cross-volume remote edges must be client-side `(sourceId, urn)` pairs**, not wire ids. Needs an id→URN map per source: a new REST or text-frame lookup, since the wire record cannot carry it. `initialGraphLoad` JSON could carry `metadata_id`/URN (V `XR-client.md:940-943` shows the frame already carries `metadata.*`).
3. **Auth is the real gap.** Reuse NIP-98 + role store + visibility filter; add a federation profile with a peer-pubkey allowlist and ReadOnly role; fix `/wss` for non-browser peers.
4. **Erasure is unspecified.** Render-only, no persistence of remote data, and a TTL-bound cache. Design a retraction signal before shipping anything that stores.
5. **Open questions to settle first:** does `/wss` serve anonymous release clients (I could not confirm); how is a peer's home host discovered from a `did:nostr`; which alignment triples live where.
