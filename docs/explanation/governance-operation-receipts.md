# Governance request and application receipts

Source qualification: 2026-09-07, EA-04. This extends the existing ACSP and decision-elevation path without claiming live relay/GitHub application or changing the configured relay's responder-authority policy.

`src/services/acsp/client.rs` persists the exact signed kind-31402 under `DATA_DIR/acsp-requests` before publishing. A kind-31403 must verify cryptographically, carry one unambiguous request `e` reference, and match the stored request's `d` identifier. The stored request must verify and belong to the local panel key. An immutable durable dispatch record is created before delivery to the actor. Missing/corrupt records, conflicting references and repeated dispatch are refused. File creation uses mode0600 and newly created directories mode0700 on Unix.

Decision-elevation requests now include the exact corpus draft/path operation. The actor refuses to publish without its durable case store and refuses a PR if decision persistence fails. `SqliteEnrichmentRepository::claim_application` conditionally moves an approved case to `applying` before the external call. Only one claimant succeeds. A confirmed PR URL advances the case to `elevating`; merge/closure remain separate observations. `applying` without a recorded PR URL is uncertain: boot does not retry or expire it as if nothing happened. An operator must inspect GitHub and reconcile the stored case before further action.

A dispatch receipt means consumer delivery was claimed; it is not proof that an actor ran. A PR URL means a PR was created, not that the corpus was merged or activated. There is no distributed transaction across relay, local journal, SQLite and GitHub. A crash between stages deliberately leaves evidence needing reconciliation. Existing legacy requests without the new request journal cannot be silently trusted after upgrade. Subscription still starts at the current timestamp, so decisions missed while offline need explicit relay recovery; this change does not invent a history replay service. Other elevation paths retain their own operation/state policies.

The configured relay remains responsible for admin admission of kind-31403; valid signatures alone are not an independent responder allowlist. Deployment must verify that relay policy and identify the exact consumer revision. No live human approval or GitHub mutation was performed by these tests.
